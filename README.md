# HomTech Supplier Hub

Отдельный внутренний сервис приобретения цифровых товаров у InterHub и будущих поставщиков.

Supplier Hub не знает о маркетплейсах, заказах Яндекса/Ozon, пулах Seller и сообщениях поддержки. Его ответственность заканчивается устойчивой идемпотентной покупкой и безопасным возвратом результата вызывающему сервису.

## Безопасность первого этапа

- реальные покупки выключены по умолчанию двумя независимыми флагами;
- сервис использует собственную PostgreSQL и не подключается к БД CRM или Seller;
- запрос сохраняется до первого обращения к поставщику;
- перед `pay` состояние фиксируется в БД;
- ошибка или таймаут после начала `pay` переводит операцию в ожидание `check_status`, а не запускает повторную оплату;
- полученный код хранится зашифрованным и не попадает в обычные ответы API или журналы;
- один `idempotency_key` нельзя повторно использовать с другими параметрами.

## Локальный запуск

1. Скопировать `.env.example` в `.env` и заменить демонстрационные секреты.
2. Запустить PostgreSQL, API и worker:

   ```bash
   docker compose up --build
   ```

3. Проверить:

   ```bash
   curl http://127.0.0.1:8010/live
   curl http://127.0.0.1:8010/ready
   ```

Worker останется в paused-режиме, пока одновременно не заданы:

```dotenv
SUPPLIER_HUB_PURCHASES_ENABLED=true
INTERHUB_PAY_ENABLED=true
```

На этапе разработки и тестирования эти значения должны оставаться `false`.

## API первого этапа

- `GET /live` — процесс API работает;
- `GET /ready` — конфигурация и отдельная БД доступны;
- `GET /v1/providers/interhub/services` — каталог InterHub;
- `GET /v1/providers/interhub/balance` — баланс InterHub;
- `POST /v1/purchases` — идемпотентно поставить одну покупку в очередь;
- `GET /v1/purchases/{id}` — состояние без раскрытия кода;
- `GET /v1/purchases/{id}/result` — получить результат успешной покупки.

Внутренние методы требуют заголовки `X-Hub-Client` и `X-Hub-Key`. Клиенты задаются JSON-объектом в `SUPPLIER_HUB_CLIENTS_JSON`.

## Состояния покупки

```text
created -> checked -> payment_started -> processing -> succeeded
    |          |                                |
    +----------+------------------------------> failed
                                               requires_attention
```

`payment_started`, `processing` и `requires_attention` запрещают вызывающему сервису переходить к следующему способу выдачи, пока фактический исход оплаты не выяснен.

## Проверки

```bash
python -m unittest discover -s tests -v
```

Живых обращений к InterHub тесты не выполняют.

Обезличенные формы реальных ответов CRM/InterHub находятся в
`tests/fixtures/interhub`. Они собраны короткими read-only запросами и
GET-вызовами каталога/баланса; платёжные методы для их получения не вызывались.
Обновлять эти файлы можно только через
`api/scripts/export_crm_interhub_fixtures.py` с повторным тестом и независимой
проверкой на секреты.
